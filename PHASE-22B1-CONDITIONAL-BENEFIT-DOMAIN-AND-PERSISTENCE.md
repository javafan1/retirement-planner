### Selected immutable definition

Plan-level conditionalBenefits: an immutable list of at most 100 immutable ConditionalBenefitDefinition records, with persistent nonzero canonical UUID, nonblank label (maximum 128 UTF-16 code units; no controls), category, closed trigger, named recipient, payment pattern, gross amount, optional not-before/end/coverage dates, escalation rate/origin, explicit tax character and receipt destination. Distinct IDs distinguish independent identical contracts. Duplicate IDs within a plan/snapshot are invalid; IDs survive every copy/Save As. No global registry or account-ID reuse is introduced. Replacing the same ID is an explicit whole-definition edit, not a second list entry.

Closed person enum: PRIMARY/SPOUSE only. Closed trigger shape: FIXED_DATE (date only), AGE (person + integer age 0–120 only), DEATH (person only). Unknown variants/irrelevant fields are rejected. Age dates derive from the frozen person's DOB using LocalDate.plusYears: February 29 becomes February 28 in a non-leap target year. No derived date is persisted. Death maps to January 1 of the scenario death year; there is no new death RNG.

Categories: CONDITIONAL_INCOME and DEATH_BENEFIT; the latter requires a named death trigger. Patterns: MONTHLY_RECURRING and ONE_TIME_LUMP_SUM. Both require a living named recipient; death trigger and recipient must differ. Any spouse role requires an actual spouse; a missing spouse is not deceased. No joint, estate or external recipient.

Monthly definitions may have not-before and end dates. Inclusive calendar-month recognition counts a partial eligible month as a whole month, restricted to the modeled interval beginning at projection opening. Effective eligibility is the later of trigger eligibility and not-before. End/coverage dates are inclusive. A pre-opening death may establish an active recurring stream. Lump sums have no monthly termination/not-before/escalation fields: one trigger event during inclusive coverage and the modeled interval, never replaying a pre-opening event. Same-day coverage is allowed when the trigger can occur on that date; death coverage must include a possible January 1. Known fixed/age trigger dates and effective commencement must be consistent with bounds. This records future evaluation semantics, not an annual evaluator.

Escalation origin: FIRST_ELIGIBLE_PAYMENT_YEAR, explicitly stored. Rate is an annual decimal fraction from 0 through 1, with no change to Pension conventions. No separate escalation date or inferred inflation linkage. Lump sums require rate zero. Monthly payments remain living-recipient-only; no after-death guarantees or payment counts.

Gross amounts are BigDecimal, 0 through 1,000,000,000,000 inclusive; precision at most 24, scale -12 through 8. Rates use the same bounded numeric representation and range 0–1. Dates are ISO strings with years 1000–9999. New definition JSON uses only a fixed, shallow property schema; unknown fields/types, scalar coercions and malformed collections are rejected locally without relaxing any global mapper. Optional dates may be missing/null; all core properties are required. No automatic IDs/default definitions are generated by deserialization.

### Tax and destination boundary

Only FULLY_TAXABLE_ORDINARY_NON_PENSION is admitted as a stored tax character. It means future modeled taxable receipt equals gross, never exceeds it, and has no pension qualification/participant facts. No federally excluded insurance category is persisted or selectable in B1; excluded principal, interest, ownership exceptions and basis require a later specialized gate. No tax calculation occurs here.

Only HOUSEHOLD_RETAINED_NON_QUALIFIED_CASH is a destination. It is a modeling pool, not a titled account. B2 must recognize cash once through settlement; no duplicate deposit, contribution, transfer, external-beneficiary or estate ledger.

## 2. Selected domain model

`domain.benefit.ConditionalBenefitDefinition` is an immutable record, including an immutable closed `Trigger` record and closed enums. There are no Person, Household, Account or UI object references in a definition. `ConditionalBenefits.validatedCopy` provides collection bounds, duplicate-ID checks and household-role validation, returning an immutable detached container.

Opaque canonical nonzero UUIDs are supplied when creating a definition; loading/copying never generates replacements. Independent identical contracts require separate IDs. Reusing an ID as a second entry is rejected; retaining an ID while replacing a definition represents editing the existing contract. Save As preserves benefit IDs while following the existing independent plan-ownership contract. No cross-plan global identity registry or account-ID scheme is introduced.

## 3. Trigger and payment contracts

| Contract | Stored shape and validation |
|---|---|
| Fixed date | Date required; person/age prohibited |
| Age | PRIMARY/SPOUSE and integer 0–120 required; independent date prohibited |
| Death | Named person required; date/age prohibited; January 1 death-year convention |
| Monthly recurring | `grossAmount` is the monthly gross amount; optional not-before and termination date; explicit annual escalation |
| One-time lump sum | `grossAmount` is the entire one-time receipt; no monthly timing or nonzero escalation |
| Death-benefit category | Requires a death trigger; does not imply tax exclusion |

The only escalation origin is FIRST_ELIGIBLE_PAYMENT_YEAR. Future annual escalation is based on the initial eligibility year after any not-before constraint, including eligibility before projection opening; it must not restart merely because a projection opens later. No payment evaluator or escalation arithmetic was added.

## 4. Recipient and event-timing policy

Only a living PRIMARY or an existing living SPOUSE can receive payments. A death-triggered definition cannot pay the same deceased trigger person. A missing spouse is rejected, not treated as dead. Single-person date/age income payable to PRIMARY is valid; no household-recipient workaround permits a single-person death payout.

Age dates use the frozen date of birth and `LocalDate.plusYears`: February 29 maps to February 28 in non-leap years. Derived dates are never persisted. Date validation is independent of the projection horizon.

Coverage qualifies the trigger event, with both boundaries inclusive; it is not a substitute for the recurring payment termination date. January 1 death events must be possible within bounded death coverage. Same-day coverage is valid where the event can occur that day. The optional monthly not-before date delays commencement to the later date; it does not rewrite the trigger. Monthly recognition will use inclusive calendar months, counting partial eligible months as whole, restricted to the modeled interval. Pre-opening deaths may activate recurring income, but pre-opening lump sums must never replay. These are B2 requirements encoded by bounded definitions and validation, not executed in B1. Legacy Pension timing is unchanged.

## 5. Tax character and destination limits

The sole stored tax character is FULLY_TAXABLE_ORDINARY_NON_PENSION. It carries no pension participant qualification and promises no insurance tax exemption. The future supported taxable amount for that category is gross receipt, never greater. Unknown tax-free, annuity-basis or insurance classifications are rejected. No excluded-income category, exclusion ratio or actual tax calculation is added.

The sole destination is HOUSEHOLD_RETAINED_NON_QUALIFIED_CASH, a modeling destination rather than legal account ownership. There are no account names, positions or retirement-account contribution assumptions. B2 must integrate this receipt once into the existing cash settlement, rather than counting both income and an extra asset deposit. External beneficiaries, estates and inherited accounts remain unsupported.

## 6. Validation and resource bounds

- At most 100 definitions; null entries and duplicate IDs rejected.
- Nonblank labels up to 128 UTF-16 code units, without ISO control characters.
- Gross amount 0–1,000,000,000,000 inclusive; BigDecimal precision at most 24 and scale −12 through 8.
- Annual decimal-fraction escalation 0–1 inclusive, with the same precision/scale bounds.
- ISO date strings, years 1000–9999; age 0–120 inclusive.
- Closed shallow trigger/payment schema; unknown fields, enum values, scalar coercions, missing/null core fields and duplicate JSON keys rejected locally.

The dedicated deserializer reads exact decimal tree values, preserving supported percentage/amount precision without floating-point conversion. Existing outer document, snapshot depth, token, raw/compressed size and numeric protections remain in place. The new limits do not tighten Pension validation.

Final boundary review added a permanent regression for death coverage beginning after January 1 of year 9999 and for coverage that cannot contain a January 1 before recurring termination. The regression failed against the initial B1 implementation, then passed after validating the earliest possible bounded event against coverage/payment end. This only validates a possible event; it does not select or execute a scenario death. A same-day covered $400,000 spouse death benefit also verifies the valid lump-sum counterpart. Before/after evidence is in target/phase22b1/boundary-before.log and boundary-after.log.

## 9. Fingerprint compatibility

`ConditionalBenefitFinancialInputs` projects nonempty definitions to an optional financial input group tagged CONDITIONAL_BENEFIT_INPUTS_V1. It removes only benefit ID/label, normalizes monetary/rate scale, sorts complete semantic definitions and retains duplicate multiplicity. Amount, category, pattern, trigger, person, recipient, timing, escalation, tax and destination fields are included. Because only one tax/destination variant is currently valid, alternative classifications are rejected rather than presented as executable choices.

`AnalysisFingerprintService` includes this group only in full-plan financial modes. SS-only fingerprints/calculations exclude it. `MonteCarloFingerprintService` includes each candidate independently without gating pure input assessment. Label/opaque-ID edits and list reordering do not change effective financial fingerprints; material edits do. Configured frozen documents deliberately retain IDs/labels, so their exact audit digests may change even where financial fingerprints remain equal.

For empty plans the group is absent, not an added empty object. Independent verification compiled the accepted HEAD versions of RetirementPlan, RetirementPlanSnapshot, CompleteProjectionSnapshot and both fingerprint services into an isolated directory, then compared them with B1 on the same synthetic inputs. All 32 output lines matched exactly: four frozen documents and 28 integrated/Monte Carlo fingerprints, covering both household types, fixed/longevity, legacy zero-expense and expense-enabled inputs. The original values are retained in the new `legacy-input-contracts.txt` test oracle. No existing financial golden was changed.
